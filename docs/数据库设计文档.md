# 语音日历 AI Native 数据库设计文档

## 1. 设计原则

- 使用 MySQL 作为业务主库。
- 使用 Flyway 管理所有结构变更。
- 表名和字段名使用英文。
- 时间字段统一使用 `datetime` 或 `timestamp`，业务默认时区为 `Asia/Shanghai`，存储层需保证可明确转换。
- 半结构化数据使用 JSON 字段，例如 AI payload、工具参数、操作快照、企业自定义字段。
- 高频查询字段必须建立索引，例如 `user_id`、`calendar_space_id`、`organization_id`、`start_time`、`status`。
- 删除业务数据优先采用软删除，保留审计和撤销能力。

## 9. 操作日志与撤销

### 9.1 operation_logs

记录所有写操作，支持 AI 撤销。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | bigint | PK | 操作日志 ID |
| user_id | bigint | FK users.id | 操作者 |
| calendar_space_id | bigint | FK calendar_spaces.id | 空间 |
| conversation_id | bigint | nullable FK ai_conversations.id | AI 会话 |
| tool_call_id | bigint | nullable FK ai_tool_call_logs.id | 工具调用 |
| operation_source | varchar(32) | not null | ai/manual/system |
| operation_type | varchar(64) | not null | create/update/delete/snooze/undo |
| target_type | varchar(64) | not null | event/reminder/notification |
| target_id | bigint | null | 目标 ID |
| before_snapshot | json | null | 修改前快照 |
| after_snapshot | json | null | 修改后快照 |
| undoable | tinyint(1) | not null default 0 | 是否可撤销 |
| undone | tinyint(1) | not null default 0 | 是否已撤销 |
| undo_expires_at | datetime | null | 撤销过期时间 |
| created_at | datetime | not null | 创建时间 |

索引：

```sql
index idx_operation_user_time (user_id, created_at)
index idx_operation_space_time (calendar_space_id, created_at)
index idx_operation_undo (user_id, operation_source, undoable, undone, undo_expires_at)
index idx_operation_target (target_type, target_id)
```

撤销规则：

- 仅撤销 `operation_source = ai` 的最近一次可撤销写操作。
- 当前时间必须小于 `undo_expires_at`。
- 目标数据 version 或快照必须匹配，避免覆盖他人后续修改。
- 撤销操作写入新的 `operation_logs`。

## 12. 推荐 Flyway 拆分

```text
V1__init_users_and_auth.sql
V2__create_spaces_and_organizations.sql
V3__create_calendar_events.sql
V4__create_event_participants.sql
V5__create_reminders_and_notifications.sql
V6__create_ai_conversations.sql
V7__create_ai_task_and_confirmations.sql
V8__create_tool_and_operation_logs.sql
V9__create_speech_and_tts_tables.sql
V10__create_view_state_and_suggestions.sql
```

原则：

- 每个 PR 只提交与当前功能相关的 migration。
- migration 文件不可修改已合并历史版本。
- 需要修复已合并结构时新增下一号 migration。
