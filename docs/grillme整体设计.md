# 语音日历 AI Native 项目设计

## 项目目标

开发一个以语音交互为核心的日历管理工具，帮助用户更高效、便捷地管理日程。系统需要支持通过语音添加、删除、查看事件和提醒，并在交互体验上体现 AI Native 特征。

## 已确认决策

### 1. 交付形态

采用 Web App 原型作为最终交付形态。

前端提供：

- 日历视图
- 事件列表
- 语音输入按钮
- AI 对话/执行反馈
- 事件与提醒状态展示

后端提供：

- 语音识别接口
- AI 意图理解与任务规划
- 日历事件管理 API
- 提醒管理 API
- 数据持久化能力

选择 Web App 的原因：

- 方便演示完整闭环
- 易于评委复现
- 适合拆分小 PR 逐步交付
- 可以同时展示语音交互、AI Agent 和日历管理能力

### 2. AI 功能定位

项目定位为 AI Native 应用，AI 不只是辅助解析文本，而是作为用户操作日历的主要入口。

用户可以通过语音或文本向 AI 表达目标，例如：

- "明天上午 10 点提醒我开周会"
- "今天下午有什么安排？"
- "删掉明天和产品评审相关的会议"
- "把下午的会议都推迟一小时"

AI 可以根据用户意图调用系统工具，直接改变日历数据。

### 3. AI 执行边界

采用分级执行策略：

- 低风险动作由 AI 直接执行
- 高风险动作由 AI 先询问确认，用户确认后再执行

低风险动作包括：

- 新增单个明确事件
- 新增单个明确提醒
- 查看日程
- 搜索事件
- 查询提醒

高风险动作包括：

- 删除事件
- 批量修改事件
- 批量删除事件
- 覆盖已有事件
- 取消提醒
- AI 匹配到多个候选事件时的操作

该策略既保留 AI Native 的直接执行体验，也降低误删、误改和批量错误操作的风险。

### 4. 核心架构

采用 AI Agent + 受控工具调用层架构。

AI Agent 负责：

- 理解用户语音或文本输入
- 判断用户意图
- 抽取事件参数
- 处理时间表达
- 判断是否需要追问或确认
- 决定调用哪个工具
- 向用户反馈执行结果

受控工具调用层负责：

- 创建事件
- 修改事件
- 删除事件
- 查询事件
- 搜索事件
- 创建提醒
- 修改提醒
- 删除提醒
- 参数校验
- 风险判断
- 冲突检测
- 操作日志记录

第一版不让 AI 直接生成 SQL 或直接写数据库。AI 只能通过预定义工具改变系统状态。

建议的工具函数包括：

```ts
createEvent(...)
updateEvent(...)
deleteEvent(...)
searchEvents(...)
listEvents(...)
createReminder(...)
updateReminder(...)
deleteReminder(...)
```

### 5. 技术栈

最终锁定采用 Vue 3 + TypeScript + Vite + Element Plus + Spring Boot + MySQL，不再更换主框架。

前端技术栈：

- Vue 3
- TypeScript
- Vite
- Element Plus
- 自研月历视图
- 自研轻量甘特视图
- SSE 客户端
- WebSocket 客户端

后端技术栈：

- Spring Boot
- Spring Security
- JWT
- MyBatis-Plus
- Flyway
- MySQL
- SSE
- WebSocket

AI/语音技术：

- OpenAI 兼容大模型接口
- Ollama 本地模型接口
- OpenAI 兼容语音识别接口
- 可扩展科大讯飞、Whisper、FunASR 等语音识别适配器
- TTS API 适配器架构

部署方式：

- 本地开发启动
- Docker Compose 一键演示

选择原因：

- Vue 3 + Vite 适合快速构建可演示的 Web App
- TypeScript 有助于约束前端事件、提醒和 AI 消息的数据结构
- Spring Boot 适合承载业务 API、工具调用层、确认机制和审计日志
- MySQL 适合持久化日历事件、提醒、AI 调用记录和操作日志
- 前后端分离架构便于按 PR 拆分和独立测试

### 6. AI 模型接入方式

AI 模型只由 Spring Boot 后端调用，前端不直接调用模型。

调用链路：

```text
前端语音/文本输入
  -> Spring Boot /api/ai/chat
  -> AI Agent
  -> 工具调用层
  -> MySQL
  -> 返回执行结果
```

后端抽象统一的模型客户端接口，例如：

```java
interface AiModelClient {
    AiResponse chat(AiRequest request);
}
```

第一版支持两类模型适配器：

- OpenAI 兼容格式模型调用
- Ollama 本地模型调用

OpenAI 兼容格式适配器用于接入支持 Chat Completions 或类似接口的云端/私有化模型服务。Ollama 适配器用于本地模型推理和离线演示场景。

选择原因：

- API Key 不暴露给前端
- 后端统一控制工具调用权限和确认策略
- 便于记录 AI 调用日志、工具调用日志和用户操作日志
- 业务层不绑定具体模型供应商
- 后续可通过配置切换模型来源

### 7. 语音识别方案

第一版直接采用后端语音识别链路，而不是只依赖浏览器 Web Speech API。

语音交互链路：

```text
用户语音
  -> 前端录音
  -> 上传音频到后端 /api/speech/transcribe
  -> 后端语音识别服务转写为文本
  -> 后端 AI Agent 理解文本意图
  -> 工具调用层执行日历操作
  -> 返回执行结果
```

前端负责：

- 获取麦克风权限
- 录制音频
- 展示录音状态
- 上传音频文件
- 展示转写文本
- 展示 AI 执行结果

后端负责：

- 接收音频文件
- 校验文件格式和大小
- 必要时进行音频转码
- 调用语音识别服务
- 返回转写文本
- 将转写文本交给 AI Agent 继续处理

后端应抽象语音识别客户端接口，例如：

```java
interface SpeechTranscriptionClient {
    TranscriptionResult transcribe(AudioInput input);
}
```

语音识别层采用多供应商适配器架构。业务层只依赖 `SpeechTranscriptionClient`，不直接绑定任何具体厂商。

第一版优先支持：

- OpenAI 兼容语音转写接口

架构上预留并支持扩展：

- 科大讯飞语音识别
- 本地 Whisper
- FunASR
- 阿里云智能语音交互
- 腾讯云语音识别
- 百度智能云语音识别
- 其他 HTTP API 或 SDK 形式的语音识别服务

建议的适配器命名：

```java
OpenAiCompatibleSpeechTranscriptionClient
XfyunSpeechTranscriptionClient
LocalWhisperSpeechTranscriptionClient
FunAsrSpeechTranscriptionClient
AliyunSpeechTranscriptionClient
TencentSpeechTranscriptionClient
BaiduSpeechTranscriptionClient
```

后端通过配置选择当前启用的语音识别供应商，例如：

```yaml
speech:
  provider: openai-compatible
```

语音识别模块需要统一处理：

- 音频格式校验
- 音频大小限制
- 采样率和编码格式
- 必要的音频转码
- 识别超时
- 识别失败重试
- 供应商错误码映射
- 转写置信度
- 中文口语标点与断句
- 转写结果日志

该设计更接近真实产品形态，也便于后续支持多种语音识别方案。

语音输入数据边界：

- 原始录音只用于语音识别
- 语音输入的目标是转成文字
- 识别完成后，后续 AI Agent 流程统一按文本意图处理
- 原始音频默认不长期保存
- 只保存转写文本和识别元数据
- 识别元数据包括供应商、耗时、状态、错误信息等
- 如需调试，可通过后端配置开启短期调试缓存

选择原因：

- 原始语音属于更敏感数据
- 保存音频会增加隐私和存储风险
- 日历操作审计主要依赖转写文本、AI 工具调用和操作日志
- 统一转为文本后，语音输入和键盘输入可以复用同一套 AI Agent 流程

### 8. 日历数据来源

第一版使用应用内自有日历数据，暂不接入真实第三方日历。

核心链路：

```text
AI Agent
  -> CalendarTool
  -> CalendarService
  -> MySQL 自有日历数据
```

暂不接入第三方日历的原因：

- 第三方日历 OAuth 权限流程复杂
- 同步冲突、外部删除、重复事件等问题会增加第一版实现成本
- 题目核心是语音交互和 AI 日历管理，而不是第三方日历同步
- 自有数据更利于稳定演示和测试

架构上预留外部日历 Provider 接口：

```java
interface CalendarProvider {
    Event createEvent(...);
    Event updateEvent(...);
    void deleteEvent(...);
    List<Event> listEvents(...);
}
```

第一版实现：

```java
MysqlCalendarProvider
```

后续可扩展：

- Google Calendar Provider
- Outlook Calendar Provider
- Apple Calendar Provider
- 企业微信/飞书/钉钉日历 Provider

### 9. 日志与可视化展示

日志不只作为后端排错信息，也作为 AI Native 产品体验的一部分进行展示。

前端需要提供美观、可读的操作日志视图，用于展示用户与 AI 的交互过程和系统执行结果。

建议展示的日志类型：

- 用户语音输入记录
- 语音转写结果
- AI 意图识别结果
- AI 工具调用记录
- 日历事件创建/修改/删除记录
- 高风险操作确认记录
- 失败原因与重试提示

日志展示建议：

- 使用时间线视图展示一次完整交互
- 用不同颜色区分用户输入、AI 思考、工具调用和执行结果
- 对成功、失败、等待确认等状态使用明确状态标识
- 展示关键结构化参数，例如事件标题、时间、提醒方式、匹配候选项
- 避免直接暴露冗长原始 JSON，默认展示摘要，支持展开查看详情

该能力有助于：

- 提升演示效果
- 解释 AI 为什么这样执行
- 方便调试语音识别和意图理解问题
- 体现 AI Agent 的工具调用过程

### 10. 用户与版本模式

系统同时支持单用户个人版和多用户企业版。

个人版定位：

- 面向单个用户管理自己的日程
- 可以使用默认个人空间
- 日历事件、提醒、AI 会话和操作日志都归属个人用户
- 适合第一版快速演示个人语音日历闭环

企业版定位：

- 面向团队或组织内多个用户协作管理日程
- 支持企业/组织空间
- 支持组织成员
- 支持成员角色和权限
- 后续可扩展共享日历、团队会议、成员空闲时间查询等能力

建议从数据模型上同时支持两种模式：

```text
users
organizations
organization_members
calendar_spaces
calendar_events
event_reminders
ai_conversations
ai_tool_call_logs
operation_logs
```

核心设计：

- `users` 表保存用户身份
- `organizations` 表保存企业/组织
- `organization_members` 表保存用户与组织关系
- `calendar_spaces` 表抽象日历空间，支持个人空间和企业空间
- 事件、提醒、AI 会话、工具调用日志和操作日志都关联 `calendar_space_id`

`calendar_spaces` 可包含：

```text
id
type: personal | organization
owner_user_id
organization_id
name
created_at
updated_at
```

个人版使用 `type = personal` 的日历空间。企业版使用 `type = organization` 的日历空间。

这样设计的好处：

- 个人版和企业版共用同一套事件、提醒、AI Agent 和日志能力
- 后续扩展企业协作时不需要重构核心表
- 可以在演示中同时展示个人日历和企业日历两个场景
- 权限判断可以围绕 `calendar_space_id` 和成员关系实现

第一版可实现：

- 默认个人用户
- 个人日历空间
- 示例企业组织
- 示例企业成员
- 个人/企业空间切换

第一版暂不强制实现完整注册登录系统，但数据库和服务层需要按个人版/企业版架构设计。

### 11. 企业版权限模型

企业版第一版采用三种角色：

- Owner
- Admin
- Member

Owner 权限：

- 管理组织
- 管理成员
- 管理所有企业日历事件
- 查看企业操作日志
- 删除或归档组织

Admin 权限：

- 创建企业日历事件
- 修改企业日历事件
- 删除企业日历事件
- 管理企业提醒
- 查看企业操作日志
- 不能删除组织

Member 权限：

- 查看企业日历
- 创建自己发起的事件
- 修改自己创建的事件
- 删除自己创建的事件
- 查看和自己相关的提醒

AI Agent 调用工具时必须遵守权限模型。

示例：

- Member 可以通过 AI 创建自己的企业事件
- Member 不能通过 AI 删除他人创建的企业事件
- Member 不能通过 AI 批量删除企业事件
- Admin 可以管理企业事件，但高风险批量操作仍需要确认
- Owner 可以管理成员和组织级设置

权限校验必须放在后端工具调用层，而不是只依赖前端按钮隐藏。

### 12. 注册认证系统

第一版实现完整注册认证系统，而不是只使用内置演示用户。

认证能力包括：

- 用户注册
- 用户登录
- 用户退出
- 当前用户信息查询
- 登录态保持
- 密码加密存储
- 受保护接口鉴权
- 前端路由登录保护
- AI 工具调用绑定当前登录用户

建议认证方式：

- 后端使用 Spring Security
- 密码使用 BCrypt 加密
- 前后端通过 JWT 或 Session 维持登录态
- API 请求统一携带认证信息
- 后端从认证上下文获取当前用户

建议第一版优先采用 JWT：

```text
用户登录
  -> 后端校验账号密码
  -> 签发 access token
  -> 前端保存 token
  -> 请求业务 API 时携带 token
  -> 后端解析 token 并注入当前用户上下文
```

注册后自动创建：

- 用户记录
- 个人日历空间
- 默认个人配置

企业版相关能力：

- 创建组织
- 加入组织
- 查询我的组织
- 切换个人/企业日历空间
- 基于组织成员角色进行权限校验

AI Agent 和工具调用层必须从后端认证上下文读取当前用户，而不能相信前端传入的 `user_id`。

### 13. 组织加入方式

企业版第一版支持创建组织和邀请码加入组织，暂不做邮件邀请。

流程：

```text
用户注册/登录
  -> 创建组织
  -> 系统生成邀请码
  -> 其他用户输入邀请码加入组织
  -> 默认角色为 Member
  -> Owner/Admin 可调整成员角色
```

组织能力包括：

- 创建组织
- 查看我的组织
- 查看组织成员
- 生成或刷新邀请码
- 使用邀请码加入组织
- 调整成员角色
- 移除组织成员

默认规则：

- 创建组织的用户自动成为 Owner
- 通过邀请码加入组织的用户默认为 Member
- Owner 可以任命 Admin
- Owner/Admin 可以管理普通 Member
- 只有 Owner 可以转让或删除组织

第一版暂不实现：

- 邮件邀请
- 短信邀请
- 加入审批流
- 企业域名自动加入

选择邀请码的原因：

- 演示稳定
- 不依赖外部邮件或短信服务
- 可以体现企业版多人协作
- 后续容易扩展为正式邀请系统

### 14. 重复事件规则

第一版支持基础重复事件，并利用 AI 能力处理更复杂的自然语言重复规则。

基础重复规则包括：

- 不重复
- 每天
- 每周
- 每月
- 每年
- 结束日期
- 重复次数

基础字段建议：

```text
repeat_type: none | daily | weekly | monthly | yearly | custom
repeat_until
repeat_count
repeat_rule_text
repeat_rule_json
```

设计思路：

- 简单重复规则直接落到结构化字段
- 复杂重复规则由 AI 解析为 `custom`
- `repeat_rule_text` 保存用户原始自然语言规则
- `repeat_rule_json` 保存 AI 解析后的结构化规则
- 前端展示 AI 解析结果，让用户确认或调整

示例：

用户输入：

```text
每个月最后一个工作日下午 5 点提醒我提交月报
```

AI 解析结果：

```json
{
  "type": "custom",
  "frequency": "monthly",
  "condition": "last_workday",
  "time": "17:00",
  "title": "提交月报"
}
```

执行策略：

- 基础重复规则可由 AI 直接创建
- 复杂自定义重复规则需要用户确认
- 如果 AI 无法稳定解释规则，需要追问用户
- 自定义规则必须在日志中展示 AI 的解析结果

第一版不要求完整实现所有 RRULE 语义，但数据模型和 AI 解析链路要为复杂规则预留空间。

### 15. 提醒机制

第一版采用 WebSocket 获取提醒，并在应用内展示站内提醒。

提醒能力包括：

- 事件开始时提醒
- 提前 5 分钟提醒
- 提前 15 分钟提醒
- 提前 30 分钟提醒
- 提前 1 小时提醒
- 自定义提前时间
- 单个事件支持多个提醒时间

执行链路：

```text
后端定时任务扫描即将触发的提醒
  -> 写入 notifications 表
  -> 通过 WebSocket 推送给在线用户
  -> 前端展示站内提醒
  -> 用户标记已读或稍后提醒
```

第一版不做：

- 浏览器系统通知
- 短信提醒
- 邮件提醒
- 微信提醒
- 企业微信/飞书/钉钉提醒

选择 WebSocket + 站内提醒的原因：

- 演示效果直观
- 不依赖浏览器通知权限
- 不依赖外部消息服务
- 更容易展示提醒状态、已读状态和稍后提醒
- 后续可以扩展多渠道提醒

### 16. 稍后提醒

第一版支持稍后提醒。

固定选项：

- 5 分钟后
- 10 分钟后
- 30 分钟后

AI 可以设置稍后提醒。

示例：

```text
用户：十分钟后再提醒我
AI：已将该提醒延后 10 分钟
```

提醒状态建议：

```text
pending      待触发
sent         已推送
read         已读
snoozed      已稍后提醒
cancelled    已取消
```

稍后提醒链路：

```text
用户点击稍后提醒或通过 AI 发出稍后提醒指令
  -> 后端更新提醒状态为 snoozed
  -> 生成新的 trigger_at
  -> 到达新时间后再次通过 WebSocket 推送
```

### 17. 日历视图与排期交互

第一版采用月视图 + 日程列表 + 今日焦点，并增加拖拽调整事件时间和甘特图式排期能力。

建议页面结构：

```text
左侧：AI 语音助手 / 对话 / 日志时间线
中间：月历视图 / 甘特图排期视图
右侧：今日焦点 / 即将到来 / 提醒列表
```

基础视图包括：

- 月视图查看事件分布
- 点击日期查看当天事件
- 日程列表查看选中日期或未来事件
- 今日焦点展示当天关键安排
- 即将到来展示未来 7 天事件
- 提醒列表展示待触发、已推送、已读和稍后提醒
- AI 对话区展示语音转写、意图、工具调用和执行结果

拖拽调整事件时间：

- 支持在月视图中拖拽事件到其他日期
- 支持在甘特图式排期视图中拖拽调整开始/结束时间
- 拖拽后调用后端更新事件接口
- 后端执行权限校验、冲突检测和操作日志记录
- 企业版中拖拽他人事件必须符合角色权限
- 高风险拖拽操作需要确认，例如批量事件、重复事件、企业关键会议

甘特图式排期能力：

- 用时间轴展示一段时间内的事件分布
- 支持按个人空间或企业空间查看
- 支持不同颜色区分个人事件、企业事件、提醒状态和冲突事件
- 支持拖拽移动事件时间块
- 支持调整事件块长度来修改结束时间
- 支持展示事件冲突或过密排期

AI 与排期视图结合：

- 用户可以说“把下午的会议往后推一小时”
- AI 可以先在甘特图中展示计划调整结果
- 高风险或批量调整需要用户确认后执行
- 执行结果写入日志时间线

暂不优先实现：

- 多人空闲时间自动推荐
- 复杂资源会议室排期
- 跨时区排期优化
- 完整项目管理级甘特依赖关系

### 18. 事件冲突检测

第一版支持基础时间重叠冲突检测，AI 负责解释冲突并推荐替代时间，用户可确认后强制创建或修改。

冲突检测规则：

- 同一用户同一时间段存在重叠事件时，标记为冲突
- 企业空间中同一参与人同一时间段存在重叠事件时，标记为冲突
- 拖拽事件造成冲突时，前端即时提示，后端做最终校验
- AI 创建或修改事件时，如果发现冲突，需要解释冲突原因
- 用户可以确认后强制创建或强制修改冲突事件

示例：

```text
用户：明天下午 3 点安排产品评审
AI：你明天下午 3 点已有“客户沟通”。是否仍然创建？我也可以改到 4 点或后天上午 10 点。
```

AI 推荐替代时间时，需要参考：

- 当天后续空闲时间
- 未来 7 天空闲时间
- 用户工作时间偏好
- 企业参与人的共同空闲时间

后端需要提供冲突检测工具，例如：

```java
ConflictCheckResult checkEventConflict(CreateOrUpdateEventCommand command);
```

冲突检测属于工具调用层和业务服务层的共同责任，不能只在前端判断。

### 19. 事件参与人

个人版事件默认只有创建者。企业版事件支持多个组织内参与人。

建议数据表：

```text
calendar_events
event_participants
```

`event_participants` 字段建议：

```text
event_id
user_id
role: organizer | attendee
response_status: needs_action | accepted | declined
created_at
updated_at
```

第一版支持：

- 个人版事件默认参与人为创建者
- 企业版事件可以选择多个组织成员作为参与人
- 创建企业事件的用户默认为 organizer
- AI 可以从语音中识别参与人
- 冲突检测需要检查所有参与人的时间重叠
- Member 可以查看和自己相关的企业事件
- Admin/Owner 可以查看企业空间内全部事件

示例：

```text
用户：安排我和张三明天下午三点做产品评审
AI：识别到参与人：你、张三；时间：明天下午 3 点；主题：产品评审。
```

第一版暂不做：

- 邮件参会邀请
- 参会人接受/拒绝通知流
- 外部联系人
- 会议室资源
- 复杂参会回执流程

参与人权限和可见性必须在后端校验，不能只依赖前端过滤。

### 20. 参与人识别与消歧

AI 识别参与人时，唯一匹配直接使用；如果匹配多个或无法匹配，AI 必须追问，并支持用户手动选择。

匹配规则：

- 成员姓名唯一匹配时，直接选中
- 昵称、备注名、职位等字段唯一匹配时，直接选中
- 匹配到多个成员时，AI 展示候选列表
- 无法匹配组织成员时，AI 追问用户重新指定
- 用户可以通过前端成员选择器手动选择参与人

示例：

```text
用户：安排我和小王明天下午三点开会
AI：组织中有 2 位成员可能是“小王”，请选择参与人：王明、王磊。
```

前端交互：

- AI 对话区展示候选人
- 用户可以语音选择，例如“选王明”
- 用户也可以直接点击候选人
- 用户可以打开成员选择器手动选择
- 选择完成后，AI 继续完成事件创建流程

特殊称呼处理：

- “产品经理”如果唯一匹配职位，直接选中
- “产品经理”如果匹配多人，需要追问
- “所有人”“研发组”等群体称呼需要展示参与人列表并确认
- 找不到成员时，不自动创建外部联系人

该规则用于降低 AI 错选参与人的风险，并保证冲突检测和企业权限判断准确。

### 21. AI Agent 多轮对话

AI Agent 采用多轮对话式，并在后端持久化任务状态和待确认动作。

多轮对话能力：

- 支持信息不完整时追问
- 支持参与人消歧
- 支持时间表达补全
- 支持复杂重复规则确认
- 支持冲突处理
- 支持高风险操作确认
- 支持用户中途取消任务
- 支持用户修改已识别参数

建议数据表：

```text
ai_conversations
ai_messages
ai_task_states
pending_confirmations
```

`ai_task_states` 记录当前任务进度，例如：

```text
conversation_id
task_type: create_event | update_event | delete_event | list_events | snooze_reminder
status: collecting_info | awaiting_confirmation | executing | completed | cancelled | failed
draft_payload
missing_fields
risk_level
created_at
updated_at
```

`pending_confirmations` 记录待确认动作，例如：

```text
id
conversation_id
user_id
calendar_space_id
action_type
risk_level
summary
payload
expires_at
status: pending | confirmed | rejected | expired
```

示例流程：

```text
用户：帮我安排个会议
AI：你想安排什么主题、什么时间、哪些参与人？
用户：明天下午三点，和产品组，讨论新版排期
AI：产品组包含 5 人，明天下午三点其中 2 人有冲突。要改到四点吗？
```

后端执行原则：

- AI 每次调用工具前必须带上当前用户和当前日历空间上下文
- 信息不完整时不能强行执行
- 高风险动作必须生成 `pending_confirmations`
- 用户确认后，后端根据持久化 payload 执行，而不是重新让 AI 猜测
- 任务完成、取消或失败后必须写入日志时间线

### 22. AI 写操作撤销

第一版支持撤销最近一次 AI 执行的写操作，并通过操作日志快照实现。AI 写操作支持 10 分钟内撤销，超过后只能手动修改。

可撤销操作：

- AI 创建事件
- AI 修改事件
- AI 删除事件
- AI 创建提醒
- AI 修改提醒
- AI 稍后提醒

暂不支持撤销：

- 查看类操作
- 登录注册
- 创建组织
- 加入组织
- 成员角色变更
- 已触发且已读的通知历史

实现方式：

```text
operation_logs 保存 before_snapshot 和 after_snapshot
撤销时根据 before_snapshot 反向恢复
撤销操作本身也写入日志
```

`operation_logs` 字段建议：

```text
id
user_id
calendar_space_id
operation_source: ai | manual | system
operation_type
target_type
target_id
before_snapshot
after_snapshot
undoable
undone
created_at
```

撤销规则：

- 只允许撤销当前用户有权限访问的操作
- 只撤销最近一次可撤销 AI 写操作
- 只允许在操作完成后 10 分钟内撤销
- 超过撤销窗口后不可自动撤销，但可以手动再次修改
- 企业空间撤销也必须经过权限校验
- 如果目标数据已被其他操作修改，需要提示无法安全撤销
- 如果目标事件已被其他人修改，需要提示无法安全撤销
- 撤销成功后通过日志时间线展示
- 撤销入口展示在 AI 结果卡片和最近 AI 操作中

该能力用于降低 AI 自动执行写操作带来的风险。

### 24. 输入方式

前端支持语音输入和键盘输入双模式，其中语音是主入口，键盘是兜底入口。

交互规则：

- 左侧 AI 面板默认突出语音按钮
- 用户可以切换到键盘输入
- 语音转写结果进入同一个 AI 对话流程
- 键盘输入也进入同一个 AI Agent
- 两种输入方式共享多轮任务状态
- 两种输入方式共享确认卡片、工具调用日志和撤销能力

语音输入链路：

```text
录音
  -> 上传音频
  -> 后端语音识别
  -> 转写文本
  -> AI Agent
  -> 工具调用
```

键盘输入链路：

```text
文本输入
  -> AI Agent
  -> 工具调用
```

支持双输入的原因：

- 语音符合题目核心要求
- 键盘可以应对嘈杂环境、麦克风权限失败、识别失败等情况
- 演示更稳定
- 不影响后端架构，因为最终都转换为文本意图处理

- 标题

- 执行状态
- 可用操作，例如撤销、查看日历、继续编辑

### 26. 个人版与企业版体验定位

个人版和企业版共用底层架构，但前端体验和产品表达需要区分。

个人版定位为 AI 日程伴侣。

个人版重点：

- 更自然的对话体验
- 关注个人今天、近期、习惯和提醒
- 强调陪伴式日程管理
- 主动提醒用户安排冲突、过载、遗漏事项
- 支持个人复盘，例如“我这周最忙的是哪天”
- 支持个人偏好，例如工作时间、默认提醒时间、常用地点

企业版定位为语音版协作多维日历工作台，体验上接近“语音版飞书多维表格”。

企业版重点：

- 多人协作
- 结构化数据视图
- 表格化事件管理
- 多视图切换，例如日历、列表、甘特、项目维度
- 通过语音批量创建、查询、筛选、调整团队日程
- 权限、参与人、组织空间和操作日志清晰可见
- 更强调工作流、协作、可追踪和数据治理

企业版可借鉴多维表格的能力：

- 不同视图展示同一批日程数据
- 支持按项目、负责人、状态、时间筛选
- 支持字段化展示事件信息
- 支持批量操作但必须经过权限和风险确认
- 支持 AI 通过自然语言生成筛选条件或调整视图

示例：

```text
用户：显示产品组下周所有评审会议，按负责人分组
AI：已切换到企业空间，并按负责人分组展示下周评审会议。
```

底层仍保持统一：

- 统一用户和组织模型
- 统一日历空间模型
- 统一 AI Agent
- 统一工具调用层
- 统一操作日志和撤销机制
- 统一权限校验

### 27. 企业版字段化事件模型

企业版事件支持项目、负责人、状态、优先级、标签等字段化管理能力。

基础字段：

- 标题
- 开始时间
- 结束时间
- 地点
- 参与人
- 提醒
- 重复规则

协作字段：

- 项目
- 负责人
- 优先级
- 状态
- 标签
- 类型
- 备注

企业版视图能力：

- 按项目分组
- 按负责人分组
- 按状态筛选
- 按优先级排序
- 按标签筛选
- 按时间范围查看
- 在日历、列表、甘特视图之间切换

AI 能力示例：

```text
把下周所有产品评审按负责人分组
筛选出高优先级且还没完成的会议
给所有项目 Alpha 的会议加上复盘标签
```

设计目标：

- 让企业版日程不仅是时间安排，也是结构化协作数据
- 让用户可以用语音完成筛选、分组、批量修改和视图切换
- 让企业版更接近语音版多维表格工作台

第一版采用固定协作字段，并在数据模型中预留 `custom_fields`。

第一版固定字段：

```text
project
owner_user_id
status
priority
tags
event_type
notes
```

预留字段：

```text
custom_fields JSON
```

选择该方式的原因：

- 固定字段能快速形成稳定的企业版体验
- AI 更容易理解字段含义并生成查询条件
- 前端筛选、分组和排序 UI 更容易做好
- 后续可以在 `custom_fields` 上扩展企业自定义字段
- 避免第一版引入完整字段配置系统的复杂度

### 28. 企业版核心视图

企业版第一版支持三种核心视图：

- 表格视图
- 日历视图
- 甘特视图

三种视图共享同一批企业事件数据。

AI 可以控制视图：

```text
用户：把项目 Alpha 的高优先级会议用表格列出来
```

### 29. AI 控制前端视图与全局操作

AI 可以直接控制前端视图筛选、排序、分组和高亮。这些操作只改变当前用户的视图状态，不改变业务数据，属于低风险操作。

AI 可直接执行的视图操作：

- 切换到表格视图
- 切换到日历视图
- 切换到甘特视图
- 按项目筛选
- 按负责人分组
- 按优先级排序
- 高亮冲突事件
- 展示未来 7 天
- 展示某个项目的所有会议

建议前端视图工具：

```ts
setViewMode(...)
setFilters(...)
setGroupBy(...)
setSort(...)
highlightEvents(...)
```

同时，项目整体定位为 AI Native 应用：AI 几乎可以接管所有用户可操作能力。

架构原则：

- 用户能在界面上做的操作，原则上都应该有对应的 AI 工具
- AI 通过受控工具调用层执行操作
- 所有工具调用都必须经过权限校验
- 所有写操作都必须记录日志
- 低风险操作可直接执行
- 高风险操作必须确认
- 批量操作必须确认
- 模糊匹配必须追问或让用户手动选择

AI 可接管的操作类型：

- 日程创建、修改、删除、查询
- 提醒创建、修改、取消、稍后提醒
- 视图切换、筛选、排序、分组、高亮
- 拖拽调整对应的时间修改
- 企业字段批量更新
- 参与人选择与消歧
- 冲突检测与替代时间推荐
- 操作撤销
- 日志查询与解释

需要确认的典型操作：

- 删除事件
- 批量修改事件
- 批量删除事件
- 修改重复事件规则
- 修改企业关键会议
- 影响多个参与人的改期
- 改动他人创建或负责的事件
- 企业字段批量更新

该原则确保应用不是“带 AI 聊天框的日历”，而是由 AI 作为主要操作层的日历和协作工作台。

### 30. AI Tool Registry

后端实现统一 AI Tool Registry，所有 AI 可接管操作都注册成工具。

工具分类：

```text
Calendar Tools
- create_event
- update_event
- delete_event
- list_events
- search_events
- check_conflict

Reminder Tools
- create_reminder
- snooze_reminder
- cancel_reminder
- list_reminders

View Tools
- set_view_mode
- set_filters
- set_group_by
- set_sort
- highlight_events

Enterprise Tools
- update_event_fields
- batch_update_events
- list_members
- resolve_participants

Audit Tools
- list_operation_logs
- undo_last_ai_operation
```

每个工具定义：

```text
name
description
input_schema
risk_level
required_permission
executor
```

Tool Registry 职责：

- 管理所有可被 AI 调用的工具
- 向 AI Agent 暴露工具说明和参数结构
- 根据工具风险等级决定是否需要确认
- 在执行前进行权限校验
- 在执行后记录工具调用日志和操作日志
- 统一处理工具执行异常
- 支持后续新增工具

工具执行链路：

```text
AI Agent 选择工具
  -> Tool Registry 查找工具定义
  -> 权限校验
  -> 风险判断
  -> 必要时生成待确认动作
  -> 执行工具
  -> 写入日志
  -> 返回结构化结果
```

该模块是 AI Native 架构的核心，确保 AI 能接管操作，同时保持可控、可审计、可扩展。

### 31. 工具风险等级

AI 工具采用 `low`、`medium`、`high`、`critical` 四级风险，并按风险决定是否确认。

风险等级定义：

```text
low
- 查询
- 视图切换
- 筛选排序
- 单个明确新增事件
- 单个明确新增提醒

medium
- 修改单个事件
- 稍后提醒
- 修改提醒
- 创建有冲突但用户已明确接受的事件

high
- 删除事件
- 批量修改
- 修改重复事件规则
- 修改企业事件参与人
- 影响多个参与人的改期

critical
- 批量删除
- 删除组织
- 移除成员
- 修改成员角色
- 跨企业空间操作
```

执行策略：

```text
low:
  可直接执行

medium:
  可直接执行
  必须清晰反馈
  必须尽量可撤销

high:
  必须确认
  必须记录详细日志

critical:
  必须确认
  必须校验高权限
  部分操作要求 Owner 权限
  必须记录详细日志
```

工具执行时，Tool Registry 需要综合判断：

- 工具默认风险等级
- 当前用户角色
- 当前日历空间类型
- 是否批量操作
- 是否影响他人
- 是否命中多个候选对象
- 是否修改重复事件
- 是否存在时间冲突

最终风险等级可以高于工具默认风险等级，不能低于安全判断所需等级。

### 32. 数据库与迁移方案

后端采用 MyBatis-Plus + Flyway 管理 MySQL 数据访问和迁移。

技术选择：

- MySQL：业务主库
- MyBatis-Plus：数据访问、CRUD、复杂查询、分页和条件筛选
- Flyway：数据库结构迁移管理
- JSON 字段：保存 `custom_fields`、AI payload、before/after snapshot 等半结构化数据

选择原因：

- MyBatis-Plus 适合表结构较多的业务系统
- Flyway 可以让数据库结构变更可追踪、可复现
- 方便按小 PR 提交数据库变更
- 评委或团队成员拉取项目后可以稳定初始化数据库
- 企业字段、AI 日志、工具 payload 需要部分 JSON 字段承载

数据库变更原则：

- 所有表结构变更通过 Flyway migration 提交
- 不直接依赖手动建表
- migration 文件命名清晰
- 每个 PR 只包含与当前功能相关的 migration
- 重要字段需要添加索引，例如 `user_id`、`calendar_space_id`、`organization_id`、`start_time`

### 35. AI 流式响应与实时提醒

AI 对话使用 SSE 流式响应，站内提醒继续使用 WebSocket。

SSE 用于 AI 单次请求过程：

```text
前端发送 AI 请求
  -> 后端 SSE 返回事件流
```

SSE 事件类型建议：

```text
message_delta
transcription_done
tool_call_started
tool_call_result
confirmation_required
final_result
error
```

示例流程：

```text
用户提交语音或文本
  -> message_delta: 正在理解你的请求
  -> transcription_done: 转写完成
  -> tool_call_started: 检查参与人
  -> tool_call_result: 找到参与人张三
  -> tool_call_started: 检查时间冲突
  -> tool_call_result: 无冲突
  -> tool_call_started: 创建日程
  -> final_result: 已创建日程
```

WebSocket 用于站内提醒：

```text
提醒触发
  -> 后端 WebSocket 推送
  -> 前端展示站内提醒
```

职责划分：

- SSE：AI 请求的流式过程和工具调用进度
- WebSocket：服务端主动推送站内提醒

选择原因：

- SSE 更适合一次请求对应一次流式 AI 响应
- WebSocket 更适合长期连接和提醒推送
- 两者职责清晰，便于前后端实现和调试

### 43. 时间解析与时区

第一版固定中国时区 `Asia/Shanghai`，AI 解析自然语言时间，后端负责校验并归一化。

时区策略：

- 系统默认时区为 `Asia/Shanghai`
- 前端按中国时间展示
- 后端统一处理时间归一化
- 数据库建议保存 UTC 时间或可明确转换的时间字段
- 第一版不做用户级多时区设置

自然语言时间解析：

- AI 负责理解中文口语时间表达
- 后端负责校验解析结果是否合法
- 后端负责补全标准时间格式
- 缺少日期或时间时必须追问
- 模糊表达需要追问或结合用户偏好后确认

示例：

```text
明天上午十点
下周一下午三点
月底前提醒我
下班后和张三同步
```

处理规则：

- 明确表达可直接解析
- “下班后”“晚点”“下午有空时”等模糊表达需要追问
- 如果使用用户偏好推断，必须向用户说明并等待确认
- AI 解析结果需要进入结构化卡片展示

选择原因：

- 日历应用对时间准确性要求高
- AI 适合理解中文口语，但后端必须做最终校验
- 固定中国时区可以降低第一版复杂度
- 后续可扩展多时区能力

### 44. 用户偏好设置

第一版不做用户偏好设置。

不提供：

- 默认事件时长设置
- 默认提醒时间设置
- 工作时间设置
- 每周工作日设置
- 主动建议开关设置
- 个人习惯配置

第一版采用系统默认值：

- 默认事件时长：60 分钟
- 默认提醒时间：提前 15 分钟
- 默认工作时间参考：09:00 - 18:00
- 默认工作日参考：周一到周五

这些默认值仅用于 AI 推断和替代时间建议。若用户表达模糊，AI 仍需要说明推断依据或追问确认。

选择原因：

- 避免增加设置页和偏好管理复杂度
- 第一版重点放在语音、AI Agent、个人/企业日历协作主流程
- 后续可以扩展个人偏好设置

### 45. TTS 语音回复

第一版支持 TTS 语音播报，使用 API 进行语音回复，同时保留文字回复和结构化卡片。

AI 输出形式：

- 自然语言文字回复
- 结构化结果卡片
- 工具调用时间线
- TTS 语音播报

TTS 链路：

```text
AI 生成最终回复文本
  -> 后端调用 TTS 服务
  -> 返回音频 URL 或音频流
  -> 前端播放语音回复
  -> 前端同步展示文字和卡片
```

TTS 音频存储策略：

- 第一版不长期保存 TTS 音频
- 后端生成音频后返回临时 URL 或字节流
- 临时文件短时间缓存，例如 30 分钟
- 不把每条 AI 回复音频长期入库
- 文本回复和结构化结果长期保存到会话和日志
- 如果 TTS 缓存过期，用户点击重播时重新生成

后端应抽象 TTS 客户端接口：

```java
interface TextToSpeechClient {
    TtsResult synthesize(TtsRequest request);
}
```

TTS 供应商采用适配器架构，便于扩展：

- OpenAI 兼容 TTS
- 科大讯飞语音合成
- 阿里云语音合成
- 腾讯云语音合成
- 百度智能云语音合成
- 其他 HTTP API 或 SDK 形式的 TTS 服务

播放策略：

- 个人版默认在 AI 最终回复后自动播报
- 企业版默认不自动播报，展示播放按钮
- 高风险确认问题可以播报
- 工具调用过程不逐条播报，避免打扰
- 用户可在前端暂停或重新播放
- 如果 TTS 失败，不影响文字和卡片展示

选择原因：

- 更符合语音交互产品定位
- 让个人版更像 AI 伴侣
- 保留文字和卡片可以保证信息准确可追踪
- TTS 失败时仍有稳定兜底体验

### 46. AI Prompt 与工具定义版本化

AI prompt 和 tool schema 做简单版本化，并写入会话和日志。

版本字段：

```text
ai_prompt_version
tool_schema_version
model_provider
model_name
```

写入位置：

- AI 会话
- AI 消息
- AI 工具调用日志
- 操作日志关联信息

记录原因：

- 后续调整提示词后，历史行为仍可追溯
- 后续调整工具 schema 后，历史工具调用仍可解释
- 出现 AI 行为差异时，可以定位当时使用的 prompt 和工具版本
- 增强 AI Native 项目的可观测性和工程严谨性

### 47. AI 调用指标

第一版不记录 AI token、费用等成本指标。

不记录：

- input tokens
- output tokens
- estimated_cost
- 详细费用统计
- 用户级成本统计

保留必要日志：

- 调用是否成功
- 错误码或错误信息
- 工具调用结果
- 操作日志
- 语音转写文本
- TTS 是否生成成功

选择原因：

- 降低第一版实现复杂度
- 项目重点是语音日历和 AI Agent 操作闭环
- 成本统计不是第一版核心需求
- 后续可在模型客户端层扩展更完整的指标记录

### 48. AI 思考与可解释展示

前端展示 AI 的可解释推理摘要和决策依据，用于提升透明度和用户信任。

展示内容：

- AI 识别到的用户意图
- AI 抽取出的关键参数
- AI 为什么需要追问
- AI 为什么需要确认
- AI 为什么判定为高风险操作
- AI 为什么推荐某个替代时间
- AI 调用了哪些工具
- 工具调用结果如何影响最终决策

示例：

```text
我识别到你想创建一个企业会议。
参与人包括你和张三。
时间是明天下午 3 点到 4 点。
我检查到张三在该时间已有会议，因此推荐改到下午 4 点。
```

不展示内容：

- 模型原始 chain-of-thought
- 大段系统 prompt
- 原始模型请求体
- API Key 或敏感配置
- 供应商返回的不可控内部调试信息

展示方式：

- 在 AI 对话中展示简洁解释
- 在工具调用时间线中展示执行步骤
- 在结构化卡片中展示关键参数和风险原因
- 支持展开查看更详细的工具调用摘要
- 默认展示简短摘要
- 详细推理摘要和工具过程默认折叠，用户可展开查看

该设计让用户看到 AI 的决策依据，同时避免暴露敏感配置和不可控的模型内部内容。

默认摘要示例：

```text
我理解你要创建一个会议。
时间：明天下午 3 点。
参与人：张三。
发现冲突：张三已有会议。
建议：改到下午 4 点。
```

展开详情示例：

```text
转写文本
参数抽取
参与人匹配
冲突检测
风险等级
工具调用结果
```

### 49. 第一版 MVP 边界

第一版 MVP 按“能完整演示个人 AI 伴侣 + 企业协作闭环”收敛，不追求所有高级能力完整打磨。

第一版必须完成：

```text
注册登录
个人/企业空间
组织邀请码
Owner/Admin/Member 权限
事件 CRUD
提醒 + WebSocket 站内提醒
语音转文字
文本/语音双输入
AI Agent 多轮对话
Tool Registry
低风险直接执行
高风险确认
AI 写操作 10 分钟撤销
月历视图
表格视图
轻量甘特视图
AI 日志时间线
TTS 语音回复
Docker Compose 演示
```

第一版可以简化：

```text
复杂重复规则只做 AI 解析和确认，不必覆盖所有 RRULE
甘特只做轻量排期，不做项目管理依赖
企业字段固定，custom_fields 只预留
AI 主动建议做规则驱动轻量版
移动端只做基础响应式
TTS 音频只临时缓存
语音原始音频不长期保存
```

第一版暂不做：

```text
第三方日历同步
邮件/短信/微信提醒
完整自定义字段系统
保存命名视图
多语言
多时区
长期记忆
成本/token 统计
```

### 50. 默认 AI、语音识别与 TTS 供应商

MVP 默认接 OpenAI 兼容 LLM/STT/TTS，Ollama 只作为本地 LLM 备选，其他语音识别和 TTS 供应商先做架构预留。

默认配置：

```text
LLM 默认：
OpenAI Compatible

LLM 备选：
Ollama

语音识别默认：
OpenAI Compatible Speech Transcription

TTS 默认：
OpenAI Compatible TTS 或通用 HTTP TTS
```

架构预留：

```text
语音识别扩展：
科大讯飞 / Whisper / FunASR / 阿里云 / 腾讯云 / 百度

TTS 扩展：
科大讯飞 / 阿里云 / 腾讯云 / 百度
```

兜底策略：

```text
LLM 不可用：
提示 AI 服务不可用，保留手动日历操作

语音识别不可用：
提示改用键盘输入

TTS 不可用：
继续展示文字和卡片

Ollama 不可用：
不影响云端模型配置
```

选择原因：

- OpenAI 兼容接口最通用，便于接入云端或私有化模型
- Ollama 适合本地模型演示，但不强制依赖
- 其他供应商第一版只做接口抽象和适配器预留，避免 MVP 过大

## PR 拆分建议

根据提交规范，按以下小 PR 推进。整体原则是先打通普通日历和权限，再接 AI，再做语音/TTS，最后打磨工作台和演示。

1. 项目脚手架：Vue + Spring Boot + MySQL + Flyway + Docker Compose
2. 注册登录：Spring Security + JWT + 前端登录注册
3. 空间与组织：个人空间、组织、邀请码、成员角色
4. 日历核心：事件 CRUD、参与人、企业字段
5. 权限核心：Owner/Admin/Member + 个人/企业可见性
6. 前端工作台：三栏布局、月历、表格视图
7. 甘特与拖拽：轻量甘特、拖拽改期、冲突高亮
8. 提醒系统：提醒、WebSocket、站内提醒、稍后提醒
9. AI 基础：模型客户端、Tool Registry、工具调用日志
10. AI Agent：多轮对话、确认机制、撤销、SSE 流式响应
11. 语音输入：录音上传、STT、转写文本进入 Agent
12. TTS 输出：语音回复、临时缓存、播放策略
13. 企业 AI 视图：筛选、分组、排序、视图切换工具
14. 日志与可解释：时间线、结构化卡片、推理摘要折叠
15. 演示收尾：seed 数据、README、测试、视觉打磨

## 最终验收标准

最终按“可演示、可复现、关键风险可控”验收。

1. 评委能通过 README + Docker Compose 启动项目
2. 用户能注册、登录，并进入个人 AI 工作台
3. 个人版能用语音创建日程、查看日程、触发站内提醒、稍后提醒、TTS 回复
4. 企业版能创建组织、邀请码加入、切换企业空间
5. 企业版能体现 Owner/Admin/Member 权限差异
6. 企业版能创建多人事件，并做参与人识别/手动选择
7. 系统能检测基础时间冲突，并让 AI 推荐替代时间
8. AI 能低风险直接执行，高风险生成确认卡片
9. AI 写操作能在 10 分钟内撤销
10. 表格/日历/甘特三种视图可切换
11. AI 能控制筛选、分组、排序、视图切换和高亮
12. 工具调用时间线、结构化结果卡片、AI 解释摘要能正常展示
13. 语音输入失败时可退回键盘输入
14. TTS 失败时不影响文字和卡片
15. 主分支任意时间保持可运行
